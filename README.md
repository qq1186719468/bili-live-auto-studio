# B站录播姬自动上传助手

这是一个 Windows 桌面客户端和命令行工具。它复用已安装的“B站录播姬（BililiveRecorder）”进行录制，定时查询直播状态、监听录播姬成片，下播后调用 `biliup` 投稿，并用状态文件避免同一场直播被重复处理。也保留 `yt-dlp` 作为已获授权的远程直播录制后端。

> 仅录制和上传你本人拥有、或已获得明确授权的内容。使用前请遵守主播授权、著作权、隐私要求和哔哩哔哩平台规则。本项目不会绕过付费、登录或访问控制。

## 工作流程

```text
B站公开直播状态接口 → 发现开播 → 监听 B站录播姬工作目录
                                      ↓下播且文件写完
                              写入待投稿队列 → biliup 投稿
                                                    ↓失败
                                              下次启动重试
```

客户端不会修改录播姬自己的 `config.json`。当前自动投稿监听只绑定一个直播间，并把录播姬生成的多个文件作为同一稿件的多个分 P。`data/state.json` 保存已录制场次及待投稿队列，`data/bili-live-auto.log` 保存运行日志。

客户端同时观察直播状态和本地录像文件：正常下播会触发投稿；如果房间仍在直播，但本场录像文件连续 30 秒不再增长，也会按“手动停止录播”处理并投稿。点击客户端“停止”时会等待本地文件完成写入；仍在增长的文件不会被强行上传。

同一场直播可以产生多个独立录像分段。B 站接口返回的 `live_time` 只表示本场直播的开播时间；客户端使用录像路径、文件大小和最后修改时间生成分段标识，因此手动停止录播姬后再次开始录制，新分段仍会单独进入投稿队列。

“手动投稿与台账”页面会记录自动投稿、手动投稿、失败和本地扫描结果。“扫描录播目录”会快速检查工作目录下所有“房间号-主播名”录像目录以及工作目录根部的视频，不再只扫描当前房间；“扫描切片成片”会递归检查工作目录下的 `智能切片成片`，并在来源列单独标为“切片扫描”；“选择目录扫描”可作为其他目录的备用入口。小于 1 MiB 的无效碎片仍会过滤。扫描出的历史录像默认标为“未记录”，表示客户端无法确认它过去是否由其他方式投稿，不会擅自重复上传。台账中选择“切片扫描”条目执行备用投稿时会使用独立的 `[clip_upload]` 配置，不能与整场录像混选。

投稿台账支持双击或点击“编辑记录”修改标题、状态、来源、BV 号、录像路径和备注；选中多条记录后可点击“批量编辑”，统一修改状态、来源、标题、BV 号和备注，留空字段保持各条原值。“删除记录”只移除台账条目，不删除本地录像。“重新投稿”允许把已投稿记录再次提交，会保留原记录并创建新的投稿任务，执行前会明确提示可能产生重复稿件。正在投稿中的记录不能编辑、删除或再次提交。

台账来源会明确区分为“直播-自动 / 直播-本地扫描 / 直播-手动”和“切片-生成 / 切片-扫描”。批量投稿多选记录时，客户端会询问合并为一个稿件的多个分P，还是分别创建多个稿件；直播与切片不能合并，并会分别使用对应的投稿账号。

默认保留本地录像 168 小时（7 天），启动时及之后每小时执行清理。安全默认值为只删除台账确认投稿成功的录像；可以在监控页取消“仅删除已投稿成功的录像”，此时所有超过保留期且属于已配置房间的视频文件都会被删除。清理只处理房间录像目录中的 `.flv/.mp4/.mkv/.ts`，不会处理程序、配置、凭据和 `data` 目录。

启动监控前会进行两项防错校验：房间号对应的真实主播必须与填写名称一致，而且该房间必须已加入同目录的录播姬 `config.json`。名称不一致时，客户端会显示双方名称并询问是否替换。

## 环境要求

- Windows 10/11 或 Linux
- Python 3.11+
- 较新版本的 `ffmpeg`
- B站录播姬 BililiveRecorder（使用推荐的 `bililiverecorder` 后端时）
- `yt-dlp`（仅使用可选的 `yt-dlp` 后端时）
- `yt-dlp`（远程录制或在线视频智能切片时需要；客户端会优先搜索独立环境中的 `yt-dlp.exe`）
- `biliup` CLI（当前命令格式按 biliup 2026 年主线版本实现）

Windows 当前机器自带的 `ffmpeg` 如果年代较早，建议先更新。可用以下命令确认：

```powershell
python --version
ffmpeg -version
yt-dlp --version
biliup --version
```

## 安装

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -U pip
python -m pip install -e .
python -m pip install -U biliup
Copy-Item config.example.toml config.toml
```

`biliup` 也可以使用其官方 Release 中的 Windows 可执行文件。只要 `biliup --version` 能运行即可。

## 配置

编辑 `config.toml`：

1. 将 `[[rooms]].id` 改为直播间地址末尾的数字。
2. 填写主播名称，把 `enabled` 改成 `true`。
3. 先保持 `[upload].enabled = false`，只验证检测和录制。
4. 他人直播录像通常属于转载：保留 `copyright = 2`，并确认你已获得授权。
5. 根据 B 站投稿分区调整 `tid`，不要盲用示例值 `171`。
6. 在直播姬“设置 → 录制”中确认保存目录，把 `[recording].watch_dir` 改成同一目录。

使用直播姬模式时只配置自己的一个直播间：

```toml
[[rooms]]
id = 123456
name = "主播甲"
enabled = true

```

标题、简介和转载来源支持这些模板字段：`room_id`、`streamer`、`room_title`、`room_url`、`start_time`、`recorded_at`、`filename`、`filenames`。如果直播姬生成多个分段，会作为同一个稿件的多个分 P 一次提交。

## 首次运行

Windows 图形客户端：

```powershell
bili-live-auto-gui
```

或直接双击打包后的 `录播自动上传助手.exe`。客户端会从同目录的录播姬 `config.json` 读取首个房间号作为初始值，但保存设置时只写自己的 `bili_live_auto.toml`。

点击“最小化到托盘”后窗口会隐藏，监控和投稿继续在后台运行。双击托盘图标或选择“显示主窗口”可以恢复；选择“处理本场录像后退出”会先检查本场本地录像，等待有效文件进入投稿队列后再退出客户端。点击窗口右上角叉号或“退出客户端”时，会显示与当前日间/夜间主题一致的退出确认框；取消后客户端继续运行。

在 Windows 通知区域左键单击客户端图标会立即恢复窗口，并短暂设置为最前端；窗口显示后自动取消永久置顶，不会持续遮挡其他软件。

“退出客户端”按钮会先显式从 Windows Shell 注销托盘图标、停止托盘线程，再关闭窗口，避免退出后通知区域残留图标。“停止”只停止当前自动监控，不退出客户端。

客户端把投稿配置分为两个互不串用的板块：“直播录像投稿”负责下播后的整场录像、分 P 和备用手动投稿；“切片投稿设置”单独保存切片使用的 biliup 程序、登录凭据、分区、版权类型、标签和简介。两者可以使用同一账号，也可以各自扫码登录。旧配置没有 `[clip_upload]` 时会先继承直播投稿配置，保存后自动写入独立板块。

投稿设置中的版权类型使用数字：`1` 表示自制，`2` 表示转载；来自他人直播的录播或切片通常选择 `2`，并应先取得发布授权。`tid` 是 B 站投稿分区的数字 ID，不是直播间房间号，例如 `21=日常`、`138=搞笑`、`17=单机游戏`、`65=网络游戏`、`171=电子竞技`；分区可能调整，最终应以 B 站创作中心当前分类为准。客户端在整场录像和切片设置旁均提供“填写说明”按钮，并把版权类型改为只能选择 `1` 或 `2`。

窗口顶部常驻显示“投稿进度”。自动投稿、备用手动投稿和切片投稿都会更新该区域：biliup 输出百分比时显示确定进度；连接服务器或提交稿件信息时显示动态等待条；成功停在 100%，失败显示具体原因。

“智能切片”页面可以选择原始直播录像、已经生成的切片成片和可选封面，然后点击“一键投稿这个切片”。该按钮只读取 `[clip_upload]`，不会使用整场直播录像的分区、标签或凭据。原始录像用于来源信息，不会跟随切片一起上传；切片标题完全使用页面中填写的内容，不自动添加时间戳。封面通过 biliup 的 `--cover` 参数提交，结果同样写入投稿台账并标记为“切片”。切片视频只保留底部字幕，不添加左上角文字；封面保留黄色粗体主标题，但不添加额外角标。

在选择原始录像后，可以点击“智能分析（出片前审批标题）”。文件选择框支持 Ctrl/Shift 一次选择同一场直播的多个分P；客户端会按选择顺序在本地合并为统一时间轴，只转写一次并一次生成候选，避免重复操作。客户端会在内部完成本地转写、语义选段和字幕依据核验，然后先停在标题审批：候选表会同时给出视频投稿标题与黄色封面标题，选中候选后可分别修改，点击“生成选中成片”即视为审批；批量生成前也会再次确认。少于 12 分钟建议 1 条，12–20 分钟建议 2 条，20 分钟以上约每小时 4 条（最多 12 条）。候选不再只依赖少量固定热词：本地分析会覆盖婚恋、职场、收入、住房、家庭、教育、直播、网络争议、游戏、人际、情绪压力和社会现实等话题，同时识别明确观点、反问追问、冲突转折、强烈情绪、故事经历和数字信息。本地模式使用连续候选；API 模式可以为一条候选给出 1–6 个剪辑段，删除中间跑题、重复、长停顿和无意义插话，并在确有叙事必要时用倒序或插叙调整播放顺序。所有保留段拼接后的成片优先为 180–300 秒，为了保留自然开头或完整结论可浮动到 150–360 秒。标题采用“问题或冲突 + 明确观点”的较长结构，但话题和观点仍必须能在字幕依据中核验，不会凭空制造事件。同一未变更录像会复用转写缓存。

智能切片页还支持“在线视频链接”：粘贴 B 站视频等 `http/https` 链接后点击“下载并分析”，客户端会调用本机 `yt-dlp` 单视频下载到工作目录的 `智能切片来源` 文件夹，再进入同样的本地转写、API 语义分析、标题审批和成片流程。原始在线链接不会上传给模型，也不会自动投稿；请只处理你拥有或已获授权的内容。

本地 Faster-Whisper small 不降低模型、beam search、VAD 或上下文设置：转写子进程会自动检测 CUDA，支持时使用 GPU，否则为 CTranslate2 分配多 CPU 线程，并在界面显示“转写完成”提示；GPU/CUDA 不可用时会自动回退到原来的 CPU/int8 方案。

“AI 分析设置”可选接入 OpenAI 兼容中转 API，支持 Responses API、Chat Completions 和自动探测。客户端可以从 `~/.cc-switch/cc-switch.db` 只读导入 CC Switch 当前 Codex 供应商的根地址、协议、模型和密钥；根地址会自动补全 `/v1/responses` 或 `/v1/chat/completions`。密钥只保存在 `secrets/clip-ai-key.txt`，不会写入 TOML 或日志。API 请求只包含带全局时间戳和匿名 ID 的分段字幕，不包含录像文件、文件路径或主播身份。启用 AI 后，剪辑段落表、视频标题和黄色封面标题都必须由 API 返回，本地只负责字幕识别与核验：API 返回旧版 `start/end` 时会兼容为单段方案，剪辑点会吸附到附近的 Whisper 字幕边界；缺失或覆盖不全的 evidence ID 会从各个 API 保留段的本地字幕中补齐，但不会生成新的选段或标题。每个保留段至少 12 秒，段落不得重叠，拼接总时长必须在 150–360 秒内；敏感事实和数字仍要求原字幕精确支持，普通标题允许有依据的语义改写。FFmpeg 会按 API 给出的播放顺序裁剪、拼接并重新映射字幕，封面抽帧也只来自实际保留的画面。某个字幕块的 API 候选不足时会自动再请求一次补足；第二次仍不足就只保留已通过核验的 API 条目，宁可少于建议数量也不会用本地候选补位。API 断网、超时、密钥失效或没有候选通过核验时，本次不生成候选，并在界面列出主要请求或核验失败原因。只有用户明确关闭 AI 分析时才使用原有本地模式。通过核验的 API 结果会按录像与模型配置缓存，重复分析不会重复计费。

HTTPS 请求固定使用随客户端打包的最新可信 CA 集合并保持严格证书校验，可避开服务器发送过期交叉证书时 OpenSSL 误选旧链的问题。客户端不会通过关闭证书验证来绕过风险；证书仍不可信时会明确提示中转站修复证书链或切换供应商。

审核候选后可点击“生成选中成片”，也可点击“批量生成全部候选”。输出保存在工作目录的 `智能切片成片` 文件夹：视频为 1080×1920 竖屏 H.264/AAC，横屏源使用模糊背景保留完整主体，只添加底部字幕，不添加左上角文字；封面为 1280×720，保留原有黄色粗体黑描边标题。每条候选会从三个时间点抽帧并自动选择较清晰的封面，避免单帧恰好遇到运动模糊。生成完成后会把成片、封面和无时间戳标题回填到页面，但不会自动投稿。

切片底部字幕在渲染阶段统一转换为简体中文：打包客户端内置 OpenCC 的完整繁转简词典，不改变字幕时间轴和识别结果；因此即使原始转写或 API 返回内容含繁体，成片字幕仍按简体显示。

当 biliup 投稿失败时，客户端会把最后的原始错误提示一并显示和记录，而不再只显示“退出码 1”。可能被输出的 cookie、token 等凭据会自动隐藏。

本机离线切片环境保存在程序目录的 `.clip-venv-standalone`，Faster-Whisper small 模型使用 Hugging Face 本地缓存或程序目录下的 `models/faster-whisper-small`。录像的 168 小时清理只处理房间目录中的视频文件，不会删除 Python 环境、模型、转写缓存或切片工程文件。

## 开启自动投稿

先让 `biliup` 扫码登录。凭据默认写入 `secrets/cookies.json`，该目录已加入 `.gitignore`：

```powershell
bili-live-auto -c config.toml login
```

完成一次手工测试并确认分区、标签、标题和版权类型正确后，将配置改为：

```toml
[upload]
enabled = true
```

启动时，程序会先重试 `data/state.json` 中尚未成功投稿的录像。请勿把 cookies、日志或录像文件提交到 Git。

## 常见问题

### `doctor` 提示找不到程序

重新激活虚拟环境，或把 `yt-dlp`、`biliup`、`ffmpeg` 所在目录加入 `PATH`。也可以在配置里把 `recording.executable` 和 `upload.executable` 写成绝对路径。

### 直播中但录制失败

直播姬模式下，先确认直播姬已开启“本地录制”，并核对 `watch_dir`。下播后程序会等待文件大小稳定，再进入投稿队列。

如果明确要录制已获授权的远程直播，可设置 `backend = "yt-dlp"`，并安装/升级 `yt-dlp` 和 `ffmpeg`。需要登录观看时，可在 `[recording].cookie_file` 中配置由浏览器导出的 Netscape 格式 cookies。不要将 cookies 发给他人。

### 投稿失败

查看 `data/bili-live-auto.log`，再执行 `biliup --user-cookie .\secrets\cookies.json renew` 刷新登录。失败文件会保留在待投稿队列，后续启动会重试。

客户端默认使用 `--submit web`，与 B 站创作中心官网使用同一类 Web 投稿接口。`biliupR v1.2.2` 的旧版二进制虽然在帮助中列出此参数，但实际会把 `web` 错误地发送到 APP 接口，常见表现是官网能投、客户端返回 `code: 21566`。请使用项目提供的 `biliupR-web-v1.2.2\\biliup.exe`，或升级到包含 `submit_by_web` 的 biliup 版本。

投稿设置还支持定时发布、投稿后动态、仅自己可见、禁止转载和开启充电。定时发布时间按北京时间填写 `YYYY-MM-DD HH:MM`，且必须晚于当前时间至少 4 小时；留空表示立即发布。切片投稿仍默认立即发布，避免误用整场录像的定时设置。

### 下播后自动生成切片

客户端“AI 分析设置”中可开启“下播且整场投稿成功后自动生成当天切片”。整场直播稿件成功提交后，后台会对本场录像执行现有的本地转写、API 语义核验和成片渲染流程，输出到 `智能切片成片`，并在投稿台账中登记为“切片-生成 / 待投稿”。此功能只生成视频、封面和简体字幕，不会自动调用切片账号投稿；用户可在台账中审核、编辑后手动投稿。API 不可用或本地模型缺失时会记录失败原因，不影响整场直播稿件。

### 如何停止

在终端按 `Ctrl+C`。录制过程中产生的有效 `.part` 文件会在录制程序正常返回时被保留；强制关闭终端后可手工检查录像，再决定是否投稿。

## 开发与测试

```powershell
python -m unittest discover -s tests -v
```

核心代码在 `src/bili_live_auto/`：

- `api.py`：直播间短号解析与开播状态查询
- `recorder.py`：`yt-dlp` 命令构建与录像校验
- `directory_recorder.py`：录播姬工作目录监听与文件写完判定
- `gui.py`：Windows 图形客户端
- `uploader.py`：`biliup` 投稿元数据与命令构建
- `state.py`：待投稿队列及防重复状态
- `app.py`：多直播间监控和失败重试
